The case for a GraphQL experience API

PLATFORM AUG 2025 10 MIN

GraphQL is not a database query language. It is a contract between a data graph and its consumers. Most teams implement it incorrectly — they build a thin REST proxy and call it GraphQL. The opportunity is considerably larger.

The experience API pattern

An experience API sits between your internal services and your clients. It is not a general-purpose data access layer. It is a purpose-built API that serves the exact data shape that a specific experience requires.

The GraphQL experience API extends this pattern with a typed, self-documenting contract that clients can query flexibly. The server defines what is available. The client defines what it needs. The schema is the negotiation.

What this solves

At Expedia, our booking funnel required data from twelve internal services. The classic approach — client calls each service directly — produces N+1 problems, waterfall latency, and fragile client code that breaks when a service changes its response shape.

The GraphQL experience API solves this with a single gateway that orchestrates the internal calls, resolves data dependencies, and returns a composed response. The client sees one endpoint. The complexity lives behind the schema.

The resolver boundary

The critical design decision is where you draw the resolver boundary. Resolvers should map to experience data requirements, not to internal service boundaries. If your resolver structure mirrors your microservice topology, you have built a REST proxy.

The experience API is opinionated about what the product needs. The internal services are agnostic. The schema is the seam.

What we learned

Federation is harder than it looks. The tooling has improved substantially since we built ours. Start with a monolithic schema and split it when the team boundaries demand it — not before.

Schema governance matters. A GraphQL schema is a public API. Treat it accordingly: deprecation cycles, breaking-change policies, changelog.

The performance characteristics are different from REST. Understand the N+1 problem and DataLoader before you go to production.
