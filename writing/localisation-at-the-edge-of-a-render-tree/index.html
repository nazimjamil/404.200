Localisation at the edge of a render tree

WEB JUL 2024 9 MIN

Server-side localisation is a solved problem, until it isn’t. At scale, with dynamic content, across a multi-region deployment, it becomes one of the more interesting architectural problems in a web platform.

The classic approach and its limits

The classic approach: store translation strings in files, load them at application startup, interpolate at render time. This works well for small, stable string sets.

The problems emerge when:

  • Translation sets are large (hundreds of thousands of strings)
  • Content is dynamic (marketing copy that changes frequently)
  • The same string must appear in multiple forms (currency, date formats, grammatical gender)
  • You are rendering on the server and need localisation to not be on the critical path

At Expedia’s booking funnel scale, all four apply simultaneously.

Moving localisation to the edge

The approach we took was to move localisation resolution to the server-side render, but to treat it as a data dependency rather than a build-time concern.

Translation strings are fetched from a CDN-backed service at render time, keyed by locale and feature flag context. The service returns only the strings required for the current render — not the entire translation set.

This shifts the localisation concern from the bundle to the network. The bundle stays small. The network call is fast (CDN-backed, colocated with the render tier). The render is correct.

The cache layer

The critical component is the cache layer between the render tier and the localisation service. Translation strings change infrequently. The cache hit rate should be high.

We use stale-while-revalidate semantics: serve from cache immediately, revalidate in the background. The result is fast renders with eventually consistent localisation. For marketing copy, eventual consistency is acceptable.

What we learned

Treat localisation as a first-class data dependency, not a utility. It has SLOs. It has failure modes. It needs observability.

The string-in-file model does not scale to a global platform. The earlier you treat localisation as infrastructure, the better.
